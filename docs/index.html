Multi-Agent Project Orchestrator

A two-layer framework that installs reusable multi-agent workflows globally and bootstraps any repository into a structured, sprint-driven workspace — for both Claude Code and Codex CLI.

Claude Code Codex CLI Apache 2.0 Multi-agent Obsidian vault Impeccable design

Overview

The framework has two layers:

1

bootstrap.sh — installs skills, templates, and vendor MCP servers globally into ~/.claude/ and ~/.codex/. Run once per machine.

2

/init-project — generates a local multi-agent workspace inside a specific repository from a vision file. Run once per project.

Core commands

/sprintSprint-scoped entrypoint. Runs the workflow declared in the sprint task.
/run-agentAd hoc single-agent execution outside sprint files.
/run-workflowDirect multi-stage workflow outside sprint. Accepts pre-built name or dynamic chain.
/init-projectBootstrap a repo with agents, workflows, sprints, and spec.
/upgrade-projectMigrate an older initialized project to the latest format.
/migrateMove all knowledge artifacts to a centralized Obsidian vault.
/reload-projectsAuto-fill metadata for repos registered in state.json.
/critiqueStructured Impeccable design critique on a file or URL.
CLI syntax

Claude Code uses slash commands: /sprint 001. Codex CLI uses dollar-prefix: $sprint 001. All commands and examples in this doc use the Claude syntax.

Install Once

Run bootstrap.sh once per machine. It installs all global skills, templates, and vendor MCP servers.

bash bootstrap.sh                  # standard install
bash bootstrap.sh --force          # back up current install, then reinstall
bash bootstrap.sh --dry-run        # print what would happen, no writes
bash bootstrap.sh --no-mcp         # skip CVE MCP server install

Requirements: git and python3 ≥ 3.10 (for CVE MCP only). Bootstrap continues with a warning if either is missing.

What gets installed

~/.claude/ ├── skills/{init-project, sprint, run-agent, run-workflow, upgrade-project, reload-projects, migrate, push-to-github, create-pr, documentation-from-commits}/SKILL.md └── agent-setup/{VERSION, bin/, templates/} ~/.codex/ ├── skills/{init-project, sprint, run-agent, run-workflow, upgrade-project, reload-projects, migrate, push-to-github, create-pr, documentation-from-commits}/SKILL.md └── agent-setup/{VERSION, bin/, templates/} ~/.agent-setup/ └── vendor/ ├── cve-mcp-server/ # cloned + pip-installed in a local venv └── manifest.json # paths consumed by render-templates.sh
Override paths

Set CLAUDE_HOME, CODEX_HOME, or AGENT_SETUP_VENDOR before running bootstrap.sh to change the install locations.

Init a Project

Run /init-project once inside any repository. Pass an optional vision file — if omitted, the framework auto-generates one from detected context.

cd ~/your-project
claude
/init-project ./vision.md
# Obsidian vault mode — all knowledge files go to the vault
/init-project ./vision.md vault_path=~/my-vault
Idempotent

init-project never overwrites existing generated files. Use /upgrade-project to migrate an older initialized project.

What gets generated

  • AGENTS.md — quick reference for all agent roles
  • .claude/CLAUDE.md — project-level Claude instructions
  • .claude/settings.json — permissions and hooks
  • .mcp.json + .codex/config.toml — MCP servers (context7, cve-mcp)
  • .project/vision.md, state.json, sprints/, designs/, decisions/
  • agent-setup/agents/ — 6 agent definitions with memory files
  • agent-setup/workflows/ — pre-built workflow definitions
  • agent-setup/skills/ — stack-specific skill overrides
  • agent-setup/spec/engineering-standards.md

UI projects additionally get: Impeccable design skill + PRODUCT.md + DESIGN.md stubs.

sprint

The sprint-scoped entrypoint. Reads a task from the sprint file, infers its workflow, and runs multi-agent orchestration with handoff artifacts.

/sprint <sprint-number>
/sprint <sprint-number> <task-id>
/sprint <sprint-number> <task-id> <workflow-or-chain>
/sprint 001
/sprint 001 US-001
/sprint 001 US-001 analyze-design-dev-review
/sprint 001 US-001 developer-qa-reviewer-tech-lead

Behavior

  • Workflow is inferred from the sprint task Workflow: field — no need to specify it explicitly most of the time.
  • The Workflow: field accepts either a pre-built workflow filename or a dynamic agent chain (e.g. analyst-tech-lead).
  • Handoff artifacts are persisted under .project/workflows/<run-id>/.
  • Sprint task checkboxes are updated only after explicit acceptance verification.

run-agent

Ad hoc single-agent execution for tasks that don't belong to a sprint file.

/run-agent <agent> <task text>
/run-agent developer "Fix checkout race condition"
/run-agent qa-reviewer "Review recent checkout changes for regressions"
/run-agent designer "Produce mockup for the new dashboard overview"
Single-agent only

No workflow argument, no multi-agent handoffs. Use /run-workflow for chained agents.

run-workflow

Direct multi-stage workflow outside the sprint entrypoint. Each agent's output becomes the next agent's input, and all artifacts are persisted.

/run-workflow <workflow-or-chain> <task-id|task-text>
# pre-built workflow
/run-workflow analyze-design-dev-review US-005
/run-workflow spike-research "Compare hosting options for the API"

# dynamic agent chain
/run-workflow developer-qa-reviewer US-012
/run-workflow analyst-tech-lead-developer "spike on caching strategy"
/run-workflow product-owner-designer-developer-qa-reviewer US-017

How chains resolve

A hyphen-separated chain like analyst-tech-lead-developer is split on hyphens. Each segment maps to agent-setup/agents/<segment>/agent.md. Stages are constructed at runtime — no limit on chain length.

ChainStages
developer-qa-reviewer2 stages
analyst-tech-lead-developer3 stages
product-owner-designer-developer-qa-reviewer4 stages

Workflow Format

Pre-built workflows

Static definitions live at agent-setup/workflows/<name>.md. Each stage must declare these fields explicitly:

FieldPurpose
Agent:Which agent runs this stage
Inputs:Files or artifacts this stage reads
Outputs:Files this stage produces
Pass:Condition to advance to the next stage
OnFailure:What to do when the stage fails
Prose-only files not supported

Workflow files without explicit stage fields are not orchestration-safe. The runner will reject them.

MCP Servers

Every project gets two MCP servers wired automatically at init time, mirrored across both runtimes.

FileRuntimeServers
.mcp.jsonClaude Codecontext7, cve-mcp
.codex/config.tomlCodex CLIcontext7, cve-mcp

context7

Up-to-date library and framework documentation via @upstash/context7-mcp. Spawned with npx -y — no prior install needed. Set CONTEXT7_API_KEY for higher rate limits.

Use context7 to fetch the latest fastapi docs and tell me the recommended dependency pattern in 0.115.

cve-mcp

27 security tools across 21 APIs — CVE lookup, EPSS scoring, CISA KEV, MITRE ATT&CK, OSV.dev dependency scan, GitHub Security Advisories, Shodan, VirusTotal, AbuseIPDB, GreyNoise, urlscan. Vendored locally by bootstrap.sh. Works without API keys.

Use cve-mcp to scan requirements.txt and list the top 5 vulnerable packages by EPSS score.
Use cve-mcp to check whether CVE-2024-3094 (xz-utils) affects any package in our lockfile.

Optional env vars for higher quotas: NVD_API_KEY, GITHUB_TOKEN, ABUSEIPDB_KEY, GREYNOISE_API_KEY, SHODAN_KEY.

Not daemons

MCP servers are forked as stdio sub-processes when a CLI session starts, and killed when it ends. No ports opened, nothing runs in the background between sessions.

Design Quality — Impeccable

UI projects get Impeccable wired automatically — an open-source design skill (Apache 2.0) that teaches the AI 29 anti-pattern rules and a professional design vocabulary.

What it solves

Most AI-generated UIs suffer from predictable flaws: purple gradients, nested cards, low-contrast text, generic layouts. Impeccable injects deep design knowledge — typography, color, spacing, hierarchy, WCAG — on every prompt, without repeating yourself.

Auto-install on UI projects

When init-project detects a front-end stack (react, vue, next, svelte, angular, solid), it automatically:

1

Runs npx skills add pbakaus/impeccable to install the skill into .claude/skills/.

2

Generates PRODUCT.md from vision.md — audience, brand voice, anti-references.

3

Generates a DESIGN.md stub. Complete it with /impeccable document.

Manual install

npx skills add pbakaus/impeccable

# then bootstrap context:
/impeccable teach      # load context from PRODUCT.md / DESIGN.md
/impeccable document   # generate full DESIGN.md spec

Designer agent integration

The designer agent loads PRODUCT.md and DESIGN.md automatically before every action. Its Definition of Done requires zero [BLOCKING] audit findings.

/critique skill

Run a full structured critique on any design file, component, or live URL:

/critique                           # auto-detects most recent .project/designs/*.md
/critique src/components/Hero.tsx   # specific component
/critique https://your-app.dev      # live URL

Returns a Verdict / Findings / Impeccable commands to apply / Next action report, with every finding mapped to the Impeccable command that fixes it.

Push gate

push-to-github automatically runs npx impeccable detect when Impeccable is installed and the changeset touches UI files (*.tsx, *.vue, *.jsx, *.html, *.css, *.scss).

Finding severityBehaviour
[critical]Blocks the push — reports exact findings with fix commands
[warning]Reported in push summary, non-blocking
Impeccable not installedSkip silently
No UI files in changesetSkip silently

Obsidian Vault

All project knowledge files — vision, sprints, agents, workflows, spec, decisions — can live in a shared Obsidian vault instead of each repo. Only .project/state.json and .claude/ stay in the repo.

New project with vault

/init-project ./vision.md vault_path=~/my-vault

The vault is created if it does not exist. A <project-name>/ folder is created inside it.

Migrate existing project

/migrate vault_path=~/my-vault

Shows a preview and asks for confirmation before moving any files. Creates a backup under .project/upgrades/<timestamp>/.

Vault structure

~/my-vault/ ├── .obsidian/app.json ├── _index.md # all-projects index └── <project-name>/ ├── _README.md # wikilinks overview ├── vision.md ├── spec/engineering-standards.md ├── agents/<role>/{agent.md, memory.md} ├── workflows/definitions/ ├── workflows/runs/ ├── sprints/{backlog.md, sprint-NNN.md} ├── decisions/ ├── designs/ ├── spikes/ └── releases/

All skills (sprint, run-agent, run-workflow) resolve paths through vault_project_path stored in .project/state.json.

Multi-Repo Projects

Register sibling repositories in .project/state.json to give agents cross-repo awareness.

Register repos

Open .project/state.json and add entries. Only path is required:

"repos": [
  { "path": "/absolute/path/to/backend" },
  { "path": "/absolute/path/to/frontend" },
  { "path": "/absolute/path/to/mobile" }
]

Then run /reload-projects to auto-detect and fill remaining fields.

Auto-injected context

Every sprint, run-workflow, and run-agent call automatically injects a repos block:

## Available Repositories (2)
- backend [go] my-api at /path/to/backend — REST API and auth service
- frontend [node] my-dashboard at /path/to/frontend — React dashboard

Cross-repo sprint tasks

Use the optional Repos: and Depends-on: fields in sprint tasks:

# backend sprint
### US-005 — Add health check endpoint
**Repos**: backend
**Acceptance Criteria**:
- [ ] GET /health returns 200 with status payload

# frontend sprint
### US-006 — Integrate health check in dashboard
**Repos**: frontend
**Depends-on**: backend/US-005
Auto-trigger

reload-projects is also triggered automatically inside sprint, run-workflow, and run-agent whenever a repo entry has missing fields — so you never have to run it manually if you forget.

Designer — Impeccable Definition of Done

  • All acceptance criteria verified
  • Relevant spec rules (engineering-standards.md) satisfied
  • /impeccable audit run — zero [BLOCKING] findings
  • WCAG 2.1 AA verified (contrast, keyboard path, alt text, labels)
  • Memory updated (agent-setup/agents/designer/memory.md)

Adding specialized agents

Place custom agent definitions under agent-setup/agents/specialized/<name>/agent.md. They can then be used in any dynamic chain: /run-workflow <name>-developer US-012.

Memory Protocol

Every agent loads context in a fixed order before any action to maximise prompt-cache hits (static → semi-static → dynamic):

1

Static — agent-setup/spec/engineering-standards.md

2

Static — .claude/CLAUDE.md

3

Static (designer only) — PRODUCT.md + DESIGN.md if present

4

Semi-static — agent-setup/agents/<role>/memory.md

5

Dynamic — active sprint file under .project/sprints/

6

Dynamic — prior workflow artifacts under .project/workflows/<run-id>/

After acting, the agent appends a dated entry to its memory.md. Entries older than the last 10 are compacted into a summary block automatically.

Upgrade & Migrate

upgrade-project

For repositories already initialized by an older version. Preview-first, backs up before overwrite.

/upgrade-project
  • Targets only core generated files — never touches your custom edits.
  • Creates dated backups under .project/upgrades/<timestamp>/.
  • Updates workflows, session entry docs, state fields, and the README block.
  • Asks before replacing ambiguous or user-modified files.

Refreshing the framework

bash bootstrap.sh --force   # refreshes framework + pulls latest CVE MCP

Uninstall

rm -rf ~/.claude/agent-setup \
       ~/.claude/skills/{init-project,sprint,run-agent,run-workflow,upgrade-project,reload-projects,migrate,push-to-github,create-pr,documentation-from-commits}

rm -rf ~/.codex/agent-setup \
       ~/.codex/skills/{init-project,sprint,run-agent,run-workflow,upgrade-project,reload-projects,migrate,push-to-github,create-pr,documentation-from-commits}

rm -rf ~/.agent-setup    # vendored MCP servers (CVE MCP clone + venv)
